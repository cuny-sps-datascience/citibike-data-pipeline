# Data sources for the three hour Citi Bike MVP

**Reviewed:** October 15, 2026. **Proposal:** [the supplied Word document](citibike_proposal_4_pages_for_revisions.docx). **Implementation sequence:** [MVP plan](three_hour_mvp_databricks_plan.md).

Use published trips for departure labels, Open-Meteo individual forecast runs for weather, and the MTA archive for historical alert publications. Collect MTA live alerts separately for prospective scoring. Historical alert coverage and station operating histories are the first feasibility gates. The [source audit JSON](validation/data622_mvp_source_audit_2026-10-15.json) records public API probes, schemas, counts, and response hashes; it is a small evidence summary, not a downloaded modeling dataset.

**October 16 alternative-source update:** The [new investigation](alternative_data_sources.md) verifies public ctbk.dev station-status and dated information files, gtfsrt.io archived subway alerts with UTC fetch times, and historical subway GTFS versions. All 178 daily object dates per source from April 7–October 1, 2026 are accessible; three station days and one alert day have been downloaded and audited. These are candidates for a shorter 2026 station study after full coverage/identity/availability checks. Class data is one possible longer-history source; the original 2025 window and unconditional station evaluation remain gated. The earlier source findings below retain their dated scope.

**Subsequent execution:** All 534 files have now been downloaded/checksummed. The [32-station conditional pilot](station_history_pilot.md) trained in Free Edition; 31 eligible September stations yield weather MAE 3.48 versus calendar 3.63. Full alert schema starts August 7, leaving 122 earlier dates without complete fields; April–June exact alert ablation remains gated. This is a measured source-field limitation, not a Free Edition login issue.

The free [Open-Meteo access limits](https://open-meteo.com/en/pricing) currently include 600 calls/minute, 5,000/hour, 10,000/day, and 300,000/month. Multi-location or larger requests can count as multiple calls. Cache by request parameters, model run, and location; retry with backoff. Attribute Open-Meteo and the underlying providers and record transformations under the stated CC BY 4.0 data license. Public MTA and Citi Bike access does not imply identical redistribution terms; preserve each source's terms and attribution in the dataset documentation.

## Weather acquisition and timing

**Execution update:** Without the capstone cache or class tables, the public-only benchmark acquired 2,191 of 2,200 runs for one Manhattan reference point, with checksums and explicit missingness. See the [weather datasheet](weather_reference_datasheet.md) and [benchmark scope](public_only_mvp.md). The multi-cell discussion below remains the station-level extension plan.

The [Single Runs documentation](https://open-meteo.com/en/docs/single-runs-api) provides ECMWF IFS HRES from March 14, 2024, describes early data as Cycle 49R1 hindcasts, and records a change to Cycle 50R1 on May 12, 2026 at 06 UTC. Other models generally begin April 2, 2026. Pin `models=ecmwf_ifs`; record model changes. Initialization is earlier than public availability. Preserve the proposal's seven-hour delay as an **assumption**, with a 6/7/8-hour validation sensitivity check. It does not establish historical operational issuance.

The tested request used the [dedicated historical run endpoint](https://single-runs-api.open-meteo.com/v1/forecast?latitude=40.75&longitude=-73.98&hourly=temperature_2m%2Cprecipitation%2Crain%2Csnowfall%2Cwind_speed_10m&models=ecmwf_ifs&run=2025-03-01T00%3A00&forecast_days=2&timezone=UTC&wind_speed_unit=ms). It returned 48 hourly timestamps: temperature in °C, precipitation/rain in mm, snowfall in cm, and wind in m/s. Accumulation variables each had one null; null is not dry weather. One successful request establishes access, not complete archive coverage.

Keep requested coordinates and returned grid coordinates: the sample returned 40.738136, −74.04254 for the requested 40.75, −73.98. Version cell selection and the station mapping. Deduplicate shared cells instead of making a request for every station. An illustrative four-cell, four-run-per-day extraction across 549 days requires 8,784 location-run requests before warm-up and retries. Measure actual unique cells first. The capstone cache location remains to be supplied; do not assume its taxi-zone mapping applies to Citi Bike.

[Hourly variable definitions](https://open-meteo.com/en/docs) distinguish instantaneous values from preceding-hour accumulations. For a target interval `[10:00,11:00)`, precipitation stamped 11:00 describes that interval. Store interval start/end alongside valid time and test this alignment explicitly. A row after initialization can still be a forecast, so choosing the interval-ending precipitation value is not itself leakage; run availability is the relevant cutoff.

For live collection, prefer the newest eligible individual run that is actually retrievable. Use retrieval time as conservative evidence of prospective availability and record the publisher timestamp if provided. Test recent-run latency before deployment; the continuously updated forecast endpoint is a separate fallback only after its model and timestamp contract is documented. Do not silently substitute observed or reanalysis weather.

## Historical alerts and coverage limits

The [MTA metadata API](https://data.ny.gov/api/views/7kct-peq7.json) exposes `alert_id`, `event_id`, `update_number`, `date`, `agency`, `status_label`, `affected`, `header`, and `description`. Metadata describes `date` as feed publication time, but the API type is a timezone-free calendar datetime. Verify timezone and DST handling against the dictionary or timestamped examples before UTC conversion. `affected` contains routes, not structured stop coordinates. The schema has no dedicated incident-end or planned/unplanned field.

Direct queries on October 15 returned **68,324 subway alert revisions** in the proposed window, ending **August 11, 2026 at 23:51** in the source's timestamp representation. A daily presence query found **17 dates without records** across March 2025–July 2026: the final calendar day of every month. Counts and exact queries are retained in the audit JSON. These gaps need investigation; neither archive absence nor a quiet hour proves uninterrupted feed coverage.

Begin with **recent publication counts by route**, such as distinct events published in the preceding 60 or 180 minutes, using only versions published by the cutoff. Name these features accordingly. Historical active-incident duration, stop-specific exposure, and planned/unplanned flags require further evidence. Do not carry the final version of an incident backward or infer its resolution from a later message. A recent-publication feature also needs the full lookback window covered.

The initial spatial proxy can connect a Citi Bike station to routes serving nearby subway station centroids within 250 m or 500 m. Deduplicate complexes/events and select the radius on validation data. An alert on a route is not proof of a disruption at every stop on that route. Audit current route mappings against historical station openings and changes, retain mapping confidence, and describe route proximity as a proxy.

[Subway Data NYC](https://subwaydata.nyc/) describes reconstructed train arrival times beginning April 2021. Its [programmatic access](https://subwaydata.nyc/programmatic-access) documents daily CSVs and raw GTFS realtime archives. It does **not establish an alert-version archive suitable for this proposal**. Remove it as a confirmed alert dependency; retain it only as a possible later train-service diagnostic after a feed-content audit.

## Prospective alerts and station coverage

The [MTA live alerts endpoint](https://api-endpoint.mta.info/Dataservice/mtagtfsfeeds/camsys%2Fall-alerts) returned a protobuf feed and decoded successfully using standard GTFS realtime bindings. The sampled feed contained 480 entities, including `MTASBWY` alerts with route IDs and active periods; end times and stop IDs were sometimes absent. Keep the raw payload and timestamped versions. The [GTFS realtime specification](https://gtfs.org/documentation/realtime/reference/) defines these structures, but an active-period start is not necessarily publication time. Treat first retrieval as the conservative availability time when no earlier publication evidence exists. Cold-start alerts have unknown prior age.

The GBFS discovery probe reported **version 1.1**, despite the current [reference specification](https://gbfs.org/documentation/reference/) describing version 3.0. Parse the actual endpoint version. The station-information sample contained 2,519 current stations; this includes the system's geography and is not a verified NYC or borough cohort. Its `station_id` was a UUID and `short_name` was `5997.10`. Build an audited trip-ID ↔ GBFS-ID crosswalk using short names and corroborating coordinates/names; never join the two ID fields blindly.

Historical operating intervals must come from dated station information/status or other documented evidence. Endpoints prove activity at particular times, not continuous operation. The local `FinalProject_snapshots/station_status.json` contains one version 1.1 snapshot, timestamped September 29, 2026 at 00:21:58 UTC, with 2,520 station rows. It does not establish historical operation across the modeling window. Ask for the class's existing five-minute status and daily information tables before recreating this history. New GBFS collection cannot reconstruct 2025. If historical operation cannot be established, a positive-hour-only experiment must be labeled conditional and does not satisfy the proposed unconditional operating-station forecast.

## Acquisition handoff

### Class repository and station archive alternatives

The public [DATA622Fall2026 repository](https://github.com/georgehagstrom/DATA622Fall2026) contains the course website and teaching materials. A recursive main-branch tree review found 479 files and no station-history archive or GBFS ingestion files. The [assignment](https://georgehagstrom.github.io/DATA622Fall2026/assignments/project.html) instead identifies the class Databricks/AWS workspace as the location recording station status every five minutes and station information daily. The team's GitHub Classroom repository is a separate destination whose URL has not been supplied.

[CityBikes](https://data.citybik.es/) is a concrete public backup. Its [2025 directory](https://data.citybik.es/dumps/by-network/2025/) and [2026 directory](https://data.citybik.es/dumps/by-network/2026/) list monthly `citi-bike-nyc` Parquet files across the proposed window. The [March 2025 file](https://data.citybik.es/dumps/by-network/2025/202503-citi-bike-nyc-stats.parquet) was downloaded to the processed RAID's `modeling_exports/three_hour/source_candidates/citybikes/` directory. It is 42,353,266 bytes and contains 4,985,418 records for 2,229 station UUIDs, spanning March 1 at 00:00:34 through March 31 at 23:57:50 in its timestamp representation. All rows have `extra.renting`, `extra.returning`, and `extra.last_updated`; coordinates and station names are also present. These findings establish a usable candidate, not continuous operating exposure.

The publisher's [collector code](https://github.com/citybikes/analytics/blob/master/collect.py) currently suppresses records when bike and free-dock counts are unchanged. Consequently, status-only changes may be omitted under that implementation. Audit historical collector versions, gaps, timestamp semantics, station-ID correspondence and permitted carry-forward intervals before using this archive to admit zero-hour labels. Preserve its ODbL attribution and stated database-sharing terms separately from the weather contribution. The class's raw five-minute snapshots remain preferable if their coverage is sufficient.

**Executed audit:** All 22 NYC files for November 2024–August 2026 are downloaded and checked: 145,523,643 records. Unique proximity crosswalks and bounded active brackets yield 1,123,844 conditional Manhattan hours, with just 1,655 zeros (0.147%). All main-operation eligibility flags remain false. The resulting inventory-activity selection motivated a separate Manhattan-total benchmark using complete trip inputs, rather than treating these conditional hours as unbiased station demand. See the [executed scope decision](public_only_mvp.md).

Download immutable source snapshots into a separate external-input area under the processed RAID root. Each manifest entry needs source URL, request parameters, retrieval time, checksum, source/model version, coverage interval, units, timestamp semantics, availability evidence or assumption, and collection status. Keep raw responses out of Git. Publish compact Parquet tables, a dictionary, the manifest, and coverage reports to the Free Edition workspace; retain the audit source files locally.

The strongest shared-class contribution is a documented **`nyc_weather_forecast_run`** table: one weather cell/model/run/valid-hour row, with UTC initialization and interval bounds, assumed historical availability or observed prospective retrieval, variables/units, provenance, and a hindcast flag. This remains useful even if historical alert reconstruction fails. A private Free Edition table alone does not fulfill the assignment's shared-catalog requirement; arrange import into the authorized class catalog and verify another team can query it.
